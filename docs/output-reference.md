# Output Reference

This document describes the main outputs generated by the repository.

---

## 1. Analyzer CSV outputs

The unified analyzer exports crater observables as CSV files.

### Typical contents

Each row contains:

- `filename`
- `type`
- crater observables such as:
  - `D`
  - `d_max`
  - `d_exc`
  - `mean_h_rim`
  - `V_in`
  - `V_ex`
  - `V_exc`
  - `V_cp`
  - `H_cp`
  - `epsilon`

### Typical naming patterns

Examples:

- `fluized_observables.csv`
- `fluized_observables_1_10.csv`
- `compacted_observables_25_49.csv`
- `depthMap_2_observables.csv`
- `quickmap_observables.csv`

### Overwrite behavior

If the chosen output CSV already exists, the user is prompted to:

- overwrite the file,
- or keep the existing file and create a new one with an incremented suffix.

Example:

- `fluized_observables.csv`
- `fluized_observables_1.csv`
- `fluized_observables_2.csv`

---

## 2. Fixer CSV outputs

The general fixer exports corrected crater observables after the user accepts a fix.

### Typical naming patterns

Examples:

- `compacted_fixed_observables.csv`
- `fluized_fixed_observables_1_20.csv`
- `compacted_48_obsv_ellipseFixer.csv`
- `depthMap_2_fixed_observables.csv`

### What these files represent

These CSV files store observables recomputed after:

- changing the `SurfaceType`,
- adjusting ellipse points,
- changing crop behavior,
- applying `bbox` crop,
- using `z_shift` in QuickMap / LROC workflows.

---

## 3. Profile CSV outputs

Profile-based workflows export distance-height data.

### Typical columns

- `Distance (s)`
- `Height (h)`

### Typical naming patterns

Examples:

- `fluized_35_profileFixer.csv`
- `profile_lrocFixer.csv`

These outputs are useful for:

- external plotting,
- numerical slope review,
- comparison between automatic and manual profile definitions.

---

## 4. Sensor acquisition outputs

The acquisition workflow writes depth maps to:

```text
output/depth_maps/
```

### Typical files

- `depthMap_1.npz`
- `plane_1.npz` (optional)
- `impact_1.npz` (optional)

These files can later be reused in analyzer or visualization workflows. The same output structure is used whether the source sensor was Kinect or Femto Bolt.

---

## 5. Textual correction logs

Accepted corrections are written to:

```text
output/fix_logs/fix_history.txt
```

### Log contents

Each entry records:

- timestamp,
- script name,
- dataset,
- file name,
- output CSV path,
- correction parameters,
- resulting observables,
- optional notes.

This file is useful as a lightweight audit trail for manual crater corrections.

---

## 6. Interactive plots

Some outputs are not saved automatically unless the user explicitly extends the workflow.

These include:

- 2D crater views,
- 3D crater views,
- profile plots,
- observables-vs-observables scatter plots.

At the current stage, these are displayed interactively and are intended for scientific review rather than silent batch export.

---

## 7. Suggested interpretation workflow

A practical way to use repository outputs is:

1. export analyzer CSV files,
2. compare populations by plotting observables,
3. inspect outliers visually,
4. apply corrections with the fixer,
5. review `fix_history.txt`,
6. compare original and corrected CSV outputs.

---

## 8. Notes on reproducibility

For publication-grade work, it is recommended to keep a record of:

- the exact repository version or commit,
- the Python version,
- package versions,
- the dataset source,
- the relevant output CSV names,
- the associated fix log entries.


## 9. Session summaries

Each workflow run can append to a session summary stored under:

```text
output/session_logs/
```

These session summary files may contain entries such as:

- analyzed files,
- reviewed files,
- failed files,
- corrected files,
- output files produced.


## 10. Structured session summaries

Session summaries are written under:

```text
output/session_logs/
```

They are grouped into sections such as:

- analyzed
- reviewed
- failed
- corrected
- outputs
